1. Setup and data¶

As in session 1: one thread for PyTorch and NumPy, fixed seeds, and scikit-learn's digits upsampled from 8 × 8 to 16 × 16 pixels (1,257 training and 540 test images). The real use case would be photos at 224 × 224 or more; our tiny images keep training to seconds, but they also make every layer small, which matters for latency (section 4).

This notebook also uses ONNX Runtime, a separate inference engine, to show that the same network can run at very different speeds in different runtimes (session 7 explains export and runtimes properly). It is installed here; on Colab or Kaggle run pip install onnx onnxscript onnxruntime first.

def time_ms(fn, reps=200, warmup=20):
    for _ in range(warmup):
        fn()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); ts.append(time.perf_counter() - t0)
    return float(np.median(ts)) * 1e3

def compare_ms(fns, reps=200, warmup=20):          # time in turn (A, B, C, A, B, C, ...) on a shared machine
    for f in fns.values():
        for _ in range(warmup):
            f()
    ts = {k: [] for k in fns}
    for _ in range(reps):
        for k, f in fns.items():
            t0 = time.perf_counter(); f(); ts[k].append(time.perf_counter() - t0)
    return {k: float(np.median(v)) * 1e3 for k, v in ts.items()}
print(f"torch {torch.__version__}, onnxruntime {ort.__version__}, threads {torch.get_num_threads()}")

2. What a depthwise separable convolution saves, on paper and in time¶

A standard $k \times k$ convolution from $M$ to $N$ channels on an $H \times W$ output costs $H W N M k^2$ MACs. MobileNets (Howard et al. 2017) split it in two:

  • a depthwise $k \times k$ convolution: one filter per input channel, no mixing between channels ($H W M k^2$ MACs);
  • a pointwise $1 \times 1$ convolution that mixes the channels ($H W M N$ MACs).

The ratio of the costs is

$$\frac{HWMk^2 + HWMN}{HWNMk^2} = \frac{1}{N} + \frac{1}{k^2},$$

so with $k = 3$ and many output channels the saving approaches 9 times. On paper first: what is the ratio for $N = 32$? Then the cell computes the exact MACs and times one standard layer against one depthwise + pointwise pair, in PyTorch, at batch 1.

print(f"{'channels M = N':>14s} | {'size':>7s} | standard MACs | separable MACs | MAC ratio | 1/N + 1/9 | standard (ms) | separable (ms) | time ratio")

3. Two networks: a standard CNN and a MobileNet-style CNN¶

Both networks have the same shape: a 3 × 3 stem convolution with 16 channels, four blocks with 32, 32, 64 and 64 channels (the third block has stride 2, so the last two work on 8 × 8 maps), global average pooling and a linear classifier. Every convolution is followed by batch normalization and ReLU.

  • standard: each block is a 3 × 3 convolution;
  • separable: each block is a depthwise 3 × 3 convolution followed by a pointwise 1 × 1 convolution, as in MobileNetV1.

The width multiplier $\alpha$ scales every channel count (Howard et al. 2017); MACs then scale by about $\alpha^2$, because pointwise layers cost $M N$. A resolution multiplier $\rho$ shrinks the input instead and scales MACs by $\rho^2$. Both networks are trained with the same recipe (Adam with a one-cycle learning-rate schedule, 15 epochs).

def conv_bn_relu(c_in, c_out, k, stride=1, groups=1):
    return [nn.Conv2d(c_in, c_out, k, stride=stride, padding=k // 2, groups=groups, bias=False),
            nn.BatchNorm2d(c_out), nn.ReLU()]

def make_net(kind, alpha=1.0):
    ch = [max(4, round(c * alpha)) for c in (16, 32, 32, 64, 64)]
    layers = conv_bn_relu(1, ch[0], 3)                                   # stem: an ordinary 3 x 3 convolution
    for c_in, c_out, stride in zip(ch[:-1], ch[1:], (1, 1, 2, 1)):
        if kind == "standard":
            layers += conv_bn_relu(c_in, c_out, 3, stride)
        else:                                                            # depthwise 3 x 3, then pointwise 1 x 1
            layers += conv_bn_relu(c_in, c_in, 3, stride, groups=c_in) + conv_bn_relu(c_in, c_out, 1)
    layers += [nn.AdaptiveAvgPool2d(1), nn.Flatten(), nn.Linear(ch[-1], 10)]
    return nn.Sequential(*layers)

def count(model, x):
    macs = {}
    def hook(m, inp, out):
        if isinstance(m, nn.Conv2d):
            macs[m] = out.numel() * (m.in_channels // m.groups) * m.kernel_size[0] * m.kernel_size[1]
        elif isinstance(m, nn.Linear):
            macs[m] = out.numel() * m.in_features
    handles = [m.register_forward_hook(hook) for m in model.modules()]
    with torch.inference_mode():
        model.eval()(x)
    for h in handles:
        h.remove()
    return sum(p.numel() for p in model.parameters()), sum(macs.values())

def train(model, epochs=15, lr=3e-3, bs=64, seed=0):
    g = torch.Generator().manual_seed(seed)
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    sched = torch.optim.lr_scheduler.OneCycleLR(opt, max_lr=lr, total_steps=epochs * ((len(Xtr) + bs - 1) // bs))
    model.train()
    for _ in range(epochs):
        order = torch.randperm(len(Xtr), generator=g)
        for i in range(0, len(Xtr), bs):
            b = order[i:i + bs]
            loss = F.cross_entropy(model(Xtr[b]), ytr[b])
            opt.zero_grad(); loss.backward(); opt.step(); sched.step()
    model.eval()
    with torch.inference_mode():
        return (model(Xte).argmax(1) == yte).float().mean().item()

nets, info = {}, {}
for kind in ["standard", "separable"]:
    torch.manual_seed(0)
    nets[kind] = make_net(kind)
    t0 = time.time(); acc = train(nets[kind]); t_train = time.time() - t0
    params, macs = count(nets[kind], Xte[:1])
    info[kind] = dict(acc=acc, params=params, macs=macs)
    print(f"{kind:9s}: test accuracy {acc:.3f}, {params:,d} parameters ({params * 4 / 1e3:.1f} kB in float32), "
          f"{macs:,d} MACs per image, training {t_train:.1f} s")
print(f"separable / standard: {info['separable']['params'] / info['standard']['params']:.3f} of the parameters, "
      f"{info['separable']['macs'] / info['standard']['macs']:.3f} of the MACs")

4. Did the MAC savings become time savings?¶

Now the real question: latency at batch 1, one thread, in two runtimes.

  • PyTorch eager: each layer is a separate call into PyTorch's kernels, with batch normalization as its own operation.
  • ONNX Runtime: the model is exported once to an ONNX file (torch.onnx.export(..., dynamo=True)) and run by ONNX Runtime, which fuses batch normalization into the convolutions and has its own kernels, including fast depthwise ones. The exported files go to a temporary folder. We also check that both runtimes give the same outputs.
tmp = tempfile.mkdtemp()

def to_ort(model, name):
    path = os.path.join(tmp, name + ".onnx")
    torch.onnx.export(model, (Xte[:1],), path, dynamo=True, external_data=False, verbose=False)
    opts = ort.SessionOptions()
    opts.intra_op_num_threads, opts.inter_op_num_threads = 1, 1
    sess = ort.InferenceSession(path, opts, providers=["CPUExecutionProvider"])
    name_in = sess.get_inputs()[0].name
    return (lambda x: sess.run(None, {name_in: x})[0]), os.path.getsize(path)

x1 = Xte[:1]

5. The width multiplier: an accuracy–MACs–latency trade-off¶

We train the separable network at four widths, $\alpha \in \{0.25, 0.5, 1, 2\}$, with the same recipe, and measure accuracy, MACs and batch-1 latency in both runtimes. The standard network ($\alpha = 1$) is the reference point. One seed per model: differences of a few tenths of a percent in accuracy are within seed noise (Course 1 session 9 covers seeds and error bars).

sweep = []
for alpha in [0.25, 0.5, 1.0, 2.0]:

6. Attention cost against sequence length¶

Small Transformers for phones, such as MobileViT (Mehta & Rastegari 2022), must watch the number of tokens $n$. One self-attention layer of width $d$ costs $4 n d^2$ MACs for the four projections (queries, keys, values, output) and $2 n^2 d$ MACs for the scores and the weighted values. The second term wins when $n > 2d$, and its score matrix needs $n^2$ values per head in memory. On paper first: for $d = 64$, at what $n$ do the two terms cost the same? We time PyTorch's nn.MultiheadAttention (4 heads, batch 1) as $n$ doubles.

d = 64

What to notice¶

(Written from the saved run. Counts and accuracies are the same on every run; timings vary from run to run on this shared machine, but the rankings below held in all our test runs.)

  1. The formula is exact, the speed-up is not. The MAC ratio of a standard 3 × 3 layer to a depthwise + pointwise pair matched $1/(1/N + 1/9)$ exactly, from 5.8 (16 channels) to 8.7 (256 channels). In PyTorch the separable pair was slower for 16 channels (time ratio 0.44), about equal for 32 and 64 channels (0.90 and 0.99), and faster only for 128 and 256 channels (1.89 and 1.62): never close to the MAC ratio.
  2. Much smaller, slightly less accurate. The separable network kept 0.149 of the parameters (10,474 against 70,330) and 0.139 of the MACs (989,824 against 7,115,392), and reached 0.985 test accuracy against 0.993. Its ONNX file was 67,709 bytes against 297,278. With one seed per model we cannot say whether a gap of 0.008 is real.
  3. In PyTorch eager the MAC savings did not become time savings. At batch 1 the separable network took 0.635 ms against 0.457 ms for the standard one: a speed-up of 0.72, so it was slower, with 7.2 times fewer MACs. It has nine convolutions, each with batch norm and ReLU, against five, and in PyTorch each call costs a fixed time whatever its MACs; the depthwise calls are slow besides (section 2).
  4. In ONNX Runtime they did, in part. The same two networks took 0.045 ms (separable) and 0.167 ms (standard): 3.69 times faster, about half the MAC ratio. ONNX Runtime was 2.7 times faster than PyTorch for the standard network and 14.0 times faster for the separable one, and the outputs agreed to within 2.9e-06. The runtime and its kernels decided the ranking, not the MAC count.
  5. The width multiplier trades accuracy for MACs. Widths 0.25, 0.5, 1 and 2 gave accuracies 0.791, 0.950, 0.985 and 0.994 for 100,000 to 3,552,512 MACs. At width 2 the separable network matched the standard one (0.994 against 0.993) with about half its MACs and parameters. Across the sweep the MACs grew 35 times, but PyTorch latency grew only 1.4 times (0.509 to 0.716 ms) and ONNX Runtime latency 2.3 times (0.051 to 0.116 ms): at this size, fixed per-layer costs dominate.
  6. Attention becomes quadratic. At $n = 2d = 128$ tokens the projections and the attention products both cost 2,097,152 MACs. Each doubling of $n$ multiplied the time by 1.6 to 1.9 at small $n$ and by 3.66 from 512 to 1,024 tokens, where the $n^2$ term is 89% of the MACs; the ratio approaches 4.
  7. What transfers to a phone. The counts transfer exactly. The latency ranking does not: it depends on the runtime's kernels and on the chip, as the two runtimes here showed. Phone runtimes do have optimized depthwise kernels, but whether a separable network wins on a given phone must be measured there, with the runtime you will ship (sessions 7 and 11).
