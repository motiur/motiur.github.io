1. The budget: bytes = parameters × bytes per parameter¶

A model on a phone pays for every parameter three times: in the download, in storage, and in RAM while it runs. The file size is simply parameters × bytes per parameter: 4 bytes in float32, 2 in float16, 1 in int8 and half a byte in int4 (sessions 3 and 4 show how to get there).

The first cell fixes the threads: NumPy and PyTorch each use one thread here, so that timings are repeatable on this shared machine and comparable with one phone core. The parameter counts below come from the papers and model cards (MobileNetV2: 3.4 million; Whisper tiny and base: 39 and 74 million); the 1-billion-parameter language model is a round example. The download time assumes a steady 28.26 Mbit/s, the median mobile download speed in Bangladesh in early 2025 (Ookla data, reported by DataReportal). Real speeds vary a lot, and every megabyte is also paid for.

2. Three small models, trained on digits¶

We use scikit-learn's 1,797 handwritten digits (8 × 8 pixels), upsampled to 16 × 16 by repeating each pixel (np.kron), with 1,257 images for training and 540 for testing. Three models of similar accuracy but very different shape:

  • an MLP (multi-layer perceptron): 256 → 128 → 64 → 10;
  • a small CNN: two 3 × 3 convolutions (8 and 16 channels) with max-pooling, then a linear layer;
  • a tiny Transformer: the image is cut into 16 patches of 4 × 4 pixels, each patch becomes a 64-dimensional token, and one Transformer block (4 attention heads, MLP width 256) mixes them.

The MatMul module wraps a @ b so that the forward hooks in section 3 can see the attention products. Training takes a few seconds per model.

digits = load_digits()
X16 = np.kron(digits.images.astype(np.float32) / 16.0, np.ones((1, 2, 2), dtype=np.float32))   # (1797, 16, 16)
perm = np.random.default_rng(0).permutation(len(digits.target))
tr, te = perm[:1257], perm[1257:]
Xtr, ytr = torch.tensor(X16[tr]).unsqueeze(1), torch.tensor(digits.target[tr])
Xte, yte = torch.tensor(X16[te]).unsqueeze(1), torch.tensor(digits.target[te])

class MatMul(nn.Module):
    def forward(self, a, b):
        return a @ b

class TinyTransformer(nn.Module):
    def __init__(self, d=64, heads=4, d_ff=256, patch=4, n_patches=16):
        super().__init__()
        self.patch, self.heads = patch, heads
        self.embed = nn.Linear(patch * patch, d)
        self.pos = nn.Parameter(torch.zeros(1, n_patches, d))
        self.ln1, self.qkv, self.proj = nn.LayerNorm(d), nn.Linear(d, 3 * d), nn.Linear(d, d)
        self.ln2, self.fc1, self.fc2 = nn.LayerNorm(d), nn.Linear(d, d_ff), nn.Linear(d_ff, d)
        self.mm_scores, self.mm_values = MatMul(), MatMul()
        self.ln_out, self.head = nn.LayerNorm(d), nn.Linear(d, 10)

    def forward(self, img):                                                 # img: (B, 1, 16, 16)
        B, p = img.shape[0], self.patch
        x = img.unfold(2, p, p).unfold(3, p, p).reshape(B, -1, p * p)      # (B, 16 patches, 16 pixels)
        x = self.embed(x) + self.pos
        n, d = x.shape[1], x.shape[2]
        hd = d // self.heads
        q, k, v = self.qkv(self.ln1(x)).view(B, n, 3, self.heads, hd).permute(2, 0, 3, 1, 4)
        att = torch.softmax(self.mm_scores(q, k.transpose(-2, -1)) / hd ** 0.5, dim=-1)
        x = x + self.proj(self.mm_values(att, v).transpose(1, 2).reshape(B, n, d))
        x = x + self.fc2(F.gelu(self.fc1(self.ln2(x))))
        return self.head(self.ln_out(x).mean(dim=1))

def make_models():
    torch.manual_seed(0)
    mlp = nn.Sequential(nn.Flatten(), nn.Linear(256, 128), nn.ReLU(), nn.Linear(128, 64), nn.ReLU(), nn.Linear(64, 10))
    torch.manual_seed(0)
    cnn = nn.Sequential(nn.Conv2d(1, 8, 3, padding=1), nn.ReLU(), nn.MaxPool2d(2),
                        nn.Conv2d(8, 16, 3, padding=1), nn.ReLU(), nn.MaxPool2d(2), nn.Flatten(), nn.Linear(256, 10))
    torch.manual_seed(0)
    return {"MLP": mlp, "CNN": cnn, "Transformer": TinyTransformer()}

def train(model, epochs, lr=3e-3, bs=64, seed=0):
    g = torch.Generator().manual_seed(seed)
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    model.train()
    for _ in range(epochs):
        order = torch.randperm(len(Xtr), generator=g)
        for i in range(0, len(Xtr), bs):
            b = order[i:i + bs]
            loss = F.cross_entropy(model(Xtr[b]), ytr[b])
            opt.zero_grad(); loss.backward(); opt.step()
    return model.eval()

def accuracy(model):
    with torch.inference_mode():
        return (model(Xte).argmax(1) == yte).float().mean().item()

models = make_models()
acc = {}
for name, epochs in [("MLP", 30), ("CNN", 30), ("Transformer", 30)]:
    t0 = time.time(); train(models[name], epochs); acc[name] = accuracy(models[name])
    print(f"{name:11s}: test accuracy {acc[name]:.3f} after {epochs} epochs ({time.time() - t0:.1f} s of training)")

3. Counting parameters and MACs: by formula, with hooks, and with PyTorch's FLOP counter¶

A multiply–accumulate operation (MAC) is one multiplication added to a running sum, $a \leftarrow a + w x$; one MAC is two floating-point operations (FLOPs). For one input:

  • a linear layer from $d_{in}$ to $d_{out}$ features, applied to $n$ tokens, has $d_{in} d_{out} + d_{out}$ parameters and $n \, d_{in} d_{out}$ MACs;
  • a $k \times k$ convolution from $C_{in}$ to $C_{out}$ channels with an $H_{out} \times W_{out}$ output has $C_{out} C_{in} k^2 + C_{out}$ parameters and $H_{out} W_{out} C_{out} C_{in} k^2$ MACs;
  • self-attention over $n$ tokens of width $d$ adds two products, scores $QK^\top$ and values $AV$, each with $n^2 d$ MACs, and no parameters.

By convention we count only the MACs of matrix products and convolutions; normalization, activations, pooling and additions have no MACs (section 7 shows that they still cost time). The forward hooks below run after every layer and compute MACs from the actual output shapes; FlopCounterMode counts FLOPs inside PyTorch, so its number divided by 2 should agree.

def linear_cost(d_in, d_out, tokens=1):                 # (parameters, MACs) with a bias
    return d_in * d_out + d_out, tokens * d_in * d_out

def conv_cost(c_in, c_out, k, h_out, w_out):            # (parameters, MACs) with a bias
    return c_out * c_in * k * k + c_out, h_out * w_out * c_out * c_in * k * k

def total(*costs):
    return sum(c[0] for c in costs), sum(c[1] for c in costs)

n, d, heads = 16, 64, 4
formula = {
    "MLP": total(linear_cost(256, 128), linear_cost(128, 64), linear_cost(64, 10)),
    "CNN": total(conv_cost(1, 8, 3, 16, 16), conv_cost(8, 16, 3, 8, 8), linear_cost(256, 10)),
    "Transformer": total(linear_cost(16, d, n), (n * d, 0),                      # patch embedding, positions
                         (2 * d, 0), linear_cost(d, 3 * d, n), (0, 2 * n * n * d), linear_cost(d, d, n),   # attention
                         (2 * d, 0), linear_cost(d, 256, n), linear_cost(256, d, n),                       # MLP
                         (2 * d, 0), linear_cost(d, 10)),                                                   # head
}

def count_macs(model, x):
    macs = {}
    def hook(m, inp, out):
        if isinstance(m, nn.Linear):
            macs[m] = out.numel() * m.in_features
        elif isinstance(m, nn.Conv2d):
            macs[m] = out.numel() * (m.in_channels // m.groups) * m.kernel_size[0] * m.kernel_size[1]
        elif isinstance(m, MatMul):
            macs[m] = out.numel() * inp[0].shape[-1]
    handles = [m.register_forward_hook(hook) for m in model.modules()]
    with torch.inference_mode():
        model(x)
    for h in handles:
        h.remove()
    return sum(macs.values())

4. Peak memory: weights plus the activations that are alive at the same time¶

While a model runs, RAM holds the weights plus the live activations: tensors that have been produced and are still needed. In a simple chain of layers (our MLP and CNN, at inference, without in-place operations), a layer needs its input and its output at the same moment, and everything earlier can be freed. So

$$\text{peak} \approx \text{weight bytes} + \max_{\text{layers}} (\text{input bytes} + \text{output bytes}).$$

Networks with branches, such as residual blocks, keep more tensors alive; session 8 computes peaks for whole graphs. Here we record every layer's input and output size with hooks, at batch 1 and at batch 256.

def chain_peak(model, x):
    sizes = []
    def hook(m, inp, out):
        view = out.data_ptr() == inp[0].data_ptr()            # Flatten returns a view: no new memory
        sizes.append((type(m).__name__, inp[0].numel() * 4, 0 if view else out.numel() * 4))
    handles = [m.register_forward_hook(hook) for m in model.modules() if len(list(m.children())) == 0]
    with torch.inference_mode():
        model(x)
    for h in handles:
        h.remove()
    worst = max(sizes, key=lambda s: s[1] + s[2])
    return sum(p.numel() for p in model.parameters()) * 4, worst

for name in ["MLP", "CNN"]:
    for B in [1, 256]:
        w_bytes, (layer, b_in, b_out) = chain_peak(models[name], Xte[:B])
        print(f"{name}, batch {B:3d}: weights {w_bytes / 1e3:7.1f} kB + live activations {(b_in + b_out) / 1e3:8.1f} kB "
              f"(at the {layer}) = peak {(w_bytes + b_in + b_out) / 1e3:8.1f} kB")

5. Latency: warm up, repeat, take the median, and watch the batch size¶

One timing run is not a measurement. The first call of a model can be slow (memory is allocated, kernels are chosen), and later calls vary because the operating system and other programs share the CPU. So we warm up first, repeat many times, and report the median. On a shared machine it also helps to time the competing models in turn (A, B, C, A, B, C, …), so that a slow moment hits all of them. Session 11 builds a full benchmark harness.

A phone app usually answers one request at a time, so batch 1 latency is what users feel. Large batches give more images per second, but each request waits for the whole batch.

def time_ms(fn, reps=50, warmup=10):
    for _ in range(warmup):
        fn()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); ts.append(time.perf_counter() - t0)
    return float(np.median(ts)) * 1e3

def compare_ms(fns, reps=50, warmup=10):
    for f in fns.values():
        for _ in range(warmup):
            f()
    ts = {k: [] for k in fns}
    for _ in range(reps):
        for k, f in fns.items():
            t0 = time.perf_counter(); f(); ts[k].append(time.perf_counter() - t0)
    return {k: float(np.median(v)) * 1e3 for k, v in ts.items()}

fresh = copy.deepcopy(models["CNN"])

    print(f"CNN, a new input shape: first call {first:.3f} ms, median of later calls {time_ms(lambda: fresh(x3), 200):.3f} ms")

6. The roofline of this CPU¶

The roofline model (Williams, Waterman & Patterson 2009) says a computation cannot run faster than either limit:

$$\text{attainable FLOP/s} = \min\big(\text{peak FLOP/s},\; I \times \text{memory bandwidth}\big), \qquad I = \frac{\text{FLOPs}}{\text{bytes moved}}.$$

$I$ is the arithmetic intensity: how much work is done per byte brought from memory. Below the ridge point $I^* = \text{peak} / \text{bandwidth}$, an operation is memory-bound; above it, compute-bound. We measure both limits on one thread: peak from a large matrix–matrix product, bandwidth from a dot product of two large arrays (each value is read once). For the bytes of each operation we count every input, weight and output once, in float32: the minimum traffic.

Bandwidth depends on where the data lives: small arrays stay in the fast caches near the core, large ones come from main memory. So we measure it at four sizes and give each operation the roof of the level its data fits in (a "hierarchical" roofline). This server has a large cache shared with other programs, so the bandwidth for big arrays moves by about 20% from moment to moment. A phone's caches are much smaller, so a model's weights almost always come from main memory. The numbers here do not transfer to a phone; the shape of the picture does.

A, Bm = torch.randn(1024, 1024), torch.randn(1024, 1024)
peak = 2 * 1024 ** 3 / (time_ms(lambda: A @ Bm, reps=15, warmup=3) / 1e3) / 1e9
bw = {}
for mb in [1, 8, 64, 256]:                                   # a dot product of two arrays reads mb MB in total
    u, w = torch.ones(mb * 2 ** 20 // 8), torch.ones(mb * 2 ** 20 // 8)
    bw[mb] = mb * 2 ** 20 / (time_ms(lambda: torch.dot(u, w), reps=40 if mb <= 8 else 15, warmup=3) / 1e3) / 1e9
del u, w
print(f"peak (1024 x 1024 matrix product, float32, 1 thread): {peak:.0f} GFLOP/s")
print("read bandwidth (dot product): " + ", ".join(f"{mb} MB {g:.1f} GB/s" for mb, g in bw.items()))
print("ridge points: " + ", ".join(f"{mb} MB level {peak / g:.1f}" for mb, g in bw.items()) + " FLOPs per byte")

def level(working_set):                                       # the smallest measured size the data fits in
    return next((mb for mb in bw if working_set <= 1.1 * mb * 2 ** 20), 256)

7. Same MACs, different latency¶

Two linear layers with exactly the same number of MACs (16,777,216):

  • A: 4,096 → 4,096 features on 1 token. This is what a language model does for every generated token: a matrix–vector product that must read 67 MB of weights to do 2 FLOPs per weight.
  • B: 256 → 256 features on 256 tokens. A matrix–matrix product that reuses each weight 256 times.

The roofline predicts the time as $\max(\text{FLOPs}/\text{peak},\ \text{bytes}/\text{bandwidth})$. Then we time each operation of the tiny Transformer block at batch 64 on its own, and compare its share of the MACs with its share of the time.

la, lb = nn.Linear(4096, 4096), nn.Linear(256, 256)
xa, xb = torch.randn(1, 4096), torch.randn(256, 256)
pair = {"A: 4096 -> 4096, 1 token": (la, xa, 4096 * 4096, 4 * (4096 * 4096 + 4096 + 2 * 4096)),
        "B: 256 -> 256, 256 tokens": (lb, xb, 256 * 256 * 256, 4 * (256 * 256 + 256 + 2 * 256 * 256))}
with torch.inference_mode():
    res = compare_ms({k: (lambda m=m, x=x: m(x)) for k, (m, x, _, _) in pair.items()}, reps=100)
for k, (m, x, macs, nbytes) in pair.items():
    pred = max(2 * macs / (peak * 1e9), nbytes / (bw[level(nbytes)] * 1e9)) * 1e3
    print(f"{k}: {macs:,d} MACs, {nbytes / 1e6:6.2f} MB moved, measured {res[k]:.3f} ms, roofline prediction {pred:.3f} ms")
keys = list(pair)
print(f"same MACs, but A takes {res[keys[0]] / res[keys[1]]:.1f} times as long as B")

What to notice¶

(Written from the saved run. Counts and accuracies are the same on every run. Timings change from run to run on this shared machine, by up to about 2 times between our test runs, but the orderings and ratios below held in every run.)

  1. Bytes are simple arithmetic. A 1-billion-parameter model is 4,000 MB in float32 and 500 MB in int4. At a steady 28.26 Mbit/s the float32 file takes 18.9 minutes to download and the int8 file 4.7 minutes. MobileNetV2 shrinks from 13.6 MB to 3.4 MB in int8.
  2. Similar accuracy, very different costs. Test accuracy was 0.978 (MLP), 0.987 (CNN) and 0.972 (Transformer). Parameters: 41,802, 3,818 and 52,874. MACs per image: 41,600, 94,720 and 836,224. The CNN has 11 times fewer parameters than the MLP but more MACs, because a convolution reuses each weight at every position. The formulas, the hooks and FlopCounterMode agreed exactly.
  3. Either weights or activations can dominate memory. At batch 1 the MLP's peak was 168.7 kB, almost all weights (167.2 kB). The CNN's weights are only 15.3 kB, and its live activations (16.4 kB) were already larger. At batch 256 activations dominated both models (393.2 kB and 4,194.3 kB). The CNN's worst moment was its first ReLU, which writes a new 8 × 16 × 16 tensor instead of working in place.
  4. Warm up, and watch the batch size. The first call with a new input shape took 0.858 ms, five times the median of later calls (0.168 ms). At batch 1 the MLP took 0.033 ms, the CNN 0.070 ms and the Transformer 0.187 ms. From batch 1 to batch 256, the time per image fell 27 times for the MLP but only 2.9 times for the CNN.
  5. MACs did not predict time. The CNN has 8.8 times fewer MACs than the Transformer, yet at batch 256 it took almost as long per image (23.8 against 27.5 µs). It ran at 8.0 GFLOP/s, against 60.9 for the Transformer and 71.8 for the MLP: convolutions with only 1 and 8 input channels are too narrow to keep the CPU's vector units busy.
  6. The roofline explained the extremes. Peak was 155 GFLOP/s. Read bandwidth was 119 GB/s for 1 MB of data, about 29 GB/s for 8–64 MB and 17.2 GB/s for 256 MB. The one-token matrix–vector product reached 13.4 GFLOP/s, 93% of its memory roof but only 9% of peak; the 1024 × 1024 matrix product reached 149.8 GFLOP/s, 96% of peak. Two layers with exactly 16,777,216 MACs took 2.688 ms (one token, 67 MB of weights) and 0.334 ms (256 tokens, 0.79 MB), 8.1 times apart; the roofline predicted 2.312 and 0.216 ms.
  7. Some operations reach neither roof. The depthwise convolution ran at 6.7 GFLOP/s, 4% of its roof: here the limit is the kernel (the code that runs the operation), not the hardware. Session 2 shows that another runtime does much better. The linear layer on 16 tokens sits near the ridge point and reached 34% of its roof. In the Transformer block, operations with no MACs (LayerNorm, softmax, GELU and the additions) took 26% of the time.
  8. What transfers to a phone. Counts of parameters, bytes and MACs transfer exactly, and so does the shape of the roofline: one-token matrix–vector work is memory-bound on any device. The absolute numbers do not transfer. A phone core has narrower vector units, less bandwidth and much smaller caches, while this server's large shared cache made 64 MB of data almost as fast as 8 MB. The bandwidth for large arrays also moved between our test runs (from about 16 to 29 GB/s for 64 MB), so treat every roof as approximate.
