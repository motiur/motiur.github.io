1. Weights and activations of a small CNN, layer by layer¶

A phone or microcontroller keeps the model file in storage (flash), but runs it from RAM. At run time RAM must hold the weights, the activations that are still needed, and some workspace for the kernels. We start with a small MobileNetV2-style CNN for 96 × 96 colour images (session 2), with one convolution and its activation counted as one operator, and record the real size of every tensor it produces. Its weights are random: memory does not depend on their values.

We count bytes for int8 tensors (one byte per number), as a quantized model on a small device would use (sessions 3 and 10); multiply by 4 for float32. If every tensor is freed as soon as the next layer has read it, the peak is the largest input + output pair of any layer.

import os, time, tempfile, statistics

import torch, torch.nn as nn, torch.nn.functional as F
import matplotlib.pyplot as plt

    layers = [nn.Conv2d(cin, cout, k, s, k // 2, groups=groups)]
    if act:
        layers.append(nn.ReLU6())
    return nn.Sequential(*layers)

2. Execution order changes the peak¶

When a network has branches, there are several valid orders in which to run its operators, and they need different amounts of memory. Below is a block with a skip connection and two branches (each branch: expand 1 × 1, depthwise, project 1 × 1, as in section 1), on a 24 × 24 feature map. We store it as a networkx graph whose nodes are operators and whose edges are tensors flowing between them. A tensor can be freed once every operator that reads it has run; the skip connection keeps the block's input x alive until the final add.

We compute the peak for a breadth-first order (both expansions first) and a depth-first order (one branch at a time), then try every valid order.

HW = 24 * 24
size = {"x": 16 * HW, "expand1": 96 * HW, "dw1": 96 * HW, "project1": 16 * HW,
        "expand2": 96 * HW, "dw2": 96 * HW, "project2": 16 * HW, "add": 16 * HW}   # int8 bytes of each operator's output
G = nx.DiGraph()
for n, b in size.items():
    G.add_node(n, bytes=b)
G.add_edges_from([("x", "expand1"), ("expand1", "dw1"), ("dw1", "project1"), ("x", "expand2"), ("expand2", "dw2"),
                  ("dw2", "project2"), ("project1", "add"), ("project2", "add"), ("x", "add")])

def peak_memory(G, order, outputs=("add",)):
    done, live, trace = set(), {}, []
    for n in order:
        live[n] = G.nodes[n]["bytes"]                      # the output is allocated while the inputs are still alive
        trace.append(sum(live.values()))
        done.add(n)
        for t in list(live):                                 # free every tensor whose readers have all run
            if t not in outputs and all(r in done for r in G.successors(t)):
                del live[t]
    return max(trace), trace

orders = {"breadth-first": ["x", "expand1", "expand2", "dw1", "dw2", "project1", "project2", "add"],
          "depth-first": ["x", "expand1", "dw1", "project1", "expand2", "dw2", "project2", "add"]}
all_orders = list(nx.all_topological_sorts(G))
for name, order in orders.items():
    assert order in all_orders
    pk, trace = peak_memory(G, order)
    print(f"{name:13s} peak {pk:7,} bytes   live memory after each step: {trace}")
peaks = [peak_memory(G, o)[0] for o in all_orders]
print(f"{len(all_orders)} valid orders: best peak {min(peaks):,} bytes, worst {max(peaks):,} bytes")

plt.figure(figsize=(7, 3.2))
for name, order in orders.items():
    plt.step(range(1, 9), np.array(peak_memory(G, order)[1]) / 1e3, where="mid", label=name)
plt.xlabel("step (operator number in the order)"); plt.ylabel("live memory (kB, int8)")
plt.title("same block, two execution orders", fontsize=10); plt.legend(fontsize=8); plt.tight_layout(); plt.show()

3. Patch-based execution of the first layers¶

Section 1 showed that the first, high-resolution layers set the peak. Patch-based inference (MCUNetV2, Lin et al. 2021) runs those layers on one spatial patch at a time: to produce one patch of the stage's output, compute only the input region it depends on (its receptive field), push it through the layers, and write the result into the output buffer. Neighbouring patches overlap at their borders (the "halo"), so some work is repeated.

Two details make the result exactly equal to the full computation: the input crop is filled with zeros outside the image, and after every layer, positions that lie outside the real feature map are set to zero, because they stand for the next layer's zero padding. We run the first five layers of section 1 (96 × 96 × 3 to 24 × 24 × 48) with 2 × 2 up to 8 × 8 patches. The peak counts the whole input image, the whole output of the stage, and the largest input + output pair inside one patch.

stage = [m for _, m in spec[:5]]                         # 96x96x3 -> 24x24x48
geom = [(m[0].kernel_size[0], m[0].stride[0], m[0].padding[0]) for m in stage]
sizes = [96]
for k, s, p in geom:
    sizes.append((sizes[-1] + 2 * p - k) // s + 1)       # feature-map side after each layer: 96, 48, 48, 48, 48, 24

def run_layer_by_layer(x):
    peak, macs, h = 0, 0, x
    for m in stage:
        y = m(h); c = m[0]
        peak = max(peak, h.numel() + y.numel())
        macs += y.numel() * (c.in_channels // c.groups) * c.kernel_size[0] ** 2
        h = y
    return h, peak, macs

def run_patched(x, n):
    step = sizes[-1] // n
    out = torch.empty(1, stage[-1][0].out_channels, sizes[-1], sizes[-1])
    patch_peak, macs = 0, 0
    for pi in range(n):
        for pj in range(n):
            reg = [None] * len(sizes)                    # the rows and columns needed from each feature map (half-open)
            reg[-1] = ((pi * step, (pi + 1) * step), (pj * step, (pj + 1) * step))
            for i in range(len(stage) - 1, -1, -1):
                k, s, p = geom[i]; (r0, r1), (c0, c1) = reg[i + 1]
                reg[i] = ((r0 * s - p, (r1 - 1) * s - p + k), (c0 * s - p, (c1 - 1) * s - p + k))
            (r0, r1), (c0, c1) = reg[0]
            h = torch.zeros(1, 3, r1 - r0, c1 - c0)      # crop of the input, zeros outside the image
            a0, a1, b0, b1 = max(r0, 0), min(r1, 96), max(c0, 0), min(c1, 96)
            h[:, :, a0 - r0:a1 - r0, b0 - c0:b1 - c0] = x[:, :, a0:a1, b0:b1]
            for i, m in enumerate(stage):
                c = m[0]
                y = F.conv2d(h, c.weight, c.bias, c.stride, 0, 1, c.groups)   # no padding: the crop already has its border
                if len(m) > 1:
                    y = m[1](y)
                macs += y.numel() * (c.in_channels // c.groups) * c.kernel_size[0] ** 2
                (r0, r1), (c0, c1) = reg[i + 1]; side = sizes[i + 1]
                y[:, :, :max(0, -r0)] = 0; y[:, :, y.shape[2] - max(0, r1 - side):] = 0       # outside the feature map:
                y[:, :, :, :max(0, -c0)] = 0; y[:, :, :, y.shape[3] - max(0, c1 - side):] = 0  # the next layer's zero padding
                patch_peak = max(patch_peak, h.numel() + y.numel())
                h = y
            out[:, :, pi * step:(pi + 1) * step, pj * step:(pj + 1) * step] = h
    return out, patch_peak, macs

with torch.inference_mode():
    ref, full_peak, full_macs = run_layer_by_layer(x)
    print(f"layer by layer: peak {full_peak:,} bytes (int8), {full_macs:,} MACs")
    results = []
    for n in [2, 3, 4, 6, 8]:
        out, pp, macs = run_patched(x, n)
        total = x.numel() + ref.numel() + pp
        results.append((n, total, 100 * (macs / full_macs - 1)))
        print(f"{n} x {n} patches: max |difference| {(out - ref).abs().max().item():.1e} | peak {total:,} bytes "
              f"(input {x.numel():,} + output {ref.numel():,} + one patch {pp:,}) = {full_peak / total:.2f}x lower | extra MACs {results[-1][2]:.1f}%")
    t = {"layer by layer": [], "4 x 4 patches": []}
    for _ in range(3):
        run_layer_by_layer(x); run_patched(x, 4)
    for _ in range(30):
        for name, f in [("layer by layer", lambda: run_layer_by_layer(x)), ("4 x 4 patches", lambda: run_patched(x, 4))]:
            t0 = time.perf_counter(); f(); t[name].append(time.perf_counter() - t0)
    print("median time, one thread, this server CPU: " + ", ".join(f"{k} {1e3 * np.median(v):.2f} ms" for k, v in t.items()))

res = np.array(results)
fig, ax = plt.subplots(1, 2, figsize=(9, 3.2))
ax[0].plot(res[:, 0], res[:, 1] / 1e3, "o-"); ax[0].axhline(full_peak / 1e3, color="tab:red", ls="--", label="layer by layer")
ax[0].set_xlabel("patches per side"); ax[0].set_ylabel("peak memory (kB, int8)"); ax[0].legend(fontsize=8)
ax[0].set_title("peak memory of the first stage", fontsize=10)

plt.tight_layout(); plt.show()

4. The KV cache of a language model¶

A Transformer that generates text stores the keys and values of every past token in every layer, so that each new token computes only its own (Course 4 session 4). For one sequence:

$$\text{KV bytes} = 2 \times \text{layers} \times \text{KV heads} \times \text{head dimension} \times \text{tokens} \times \text{bytes per value}.$$

Grouped-query attention (GQA; Ainslie et al. 2023) lets several query heads share one key–value head, which shrinks the cache by the group size. Some models also use sliding-window attention in most layers: those layers keep only the last $w$ tokens.

The three configurations below are example configurations, of the kind used by today's open models of about 0.5–1 billion parameters; they are not taken from a specific model card. Before you rely on numbers for a real model, read num_hidden_layers, num_key_value_heads, head_dim and any sliding-window settings from its official config.json. We compute the cache at float16, int8 and int4 (ignoring the small extra cost of the int8 and int4 scales, session 4), check the formula against tensors actually allocated in PyTorch, and find the longest context whose cache fits in 1 GB (here $10^9$ bytes).

configs = {
    "A: 16 layers, 8 KV heads x 64 (32 query heads)": dict(layers=16, kv_heads=8, head_dim=64, window=None),
    "B: 28 layers, 8 KV heads x 128 (16 query heads)": dict(layers=28, kv_heads=8, head_dim=128, window=None),
    "C: 26 layers, 1 KV head x 256, 512-token window in 5 of every 6 layers": dict(layers=26, kv_heads=1, head_dim=256, window=512, every=6),
}
def kv_bytes(cfg, tokens, bytes_per_value):
    per_token_layer = 2 * cfg["kv_heads"] * cfg["head_dim"] * bytes_per_value         # keys + values
    if cfg["window"] is None:
        return cfg["layers"] * tokens * per_token_layer
    n_global = cfg["layers"] // cfg["every"]; n_local = cfg["layers"] - n_global     # local layers keep only the window
    return per_token_layer * (n_global * tokens + n_local * min(tokens, cfg["window"]))

def longest_context(cfg, bytes_per_value, budget=1e9):
    lo, hi = 0, 10**8                                      # binary search for the largest token count that fits
    while lo < hi:
        mid = (lo + hi + 1) // 2
        lo, hi = (mid, hi) if kv_bytes(cfg, mid, bytes_per_value) <= budget else (lo, mid - 1)
    return lo

5. Memory-mapping the weights¶

Runtimes such as llama.cpp can memory-map the model file: the file's bytes appear as an array, but the operating system reads a page from storage only when it is first touched, and can drop those pages again under memory pressure because they are still in the file. Loading the file normally copies everything into the app's own memory at once. We save 50 million float16 numbers (100 MB, the size of a 50-million-parameter model in float16) to a temporary file and watch the process's resident memory (RSS) in /proc/self/status (Linux only). RssFile counts pages backed by a file, RssAnon the app's own memory.

def rss_mb():
    try:
        d = {}
        for line in open("/proc/self/status"):
            if line.startswith(("RssAnon", "RssFile")):
                key, val = line.split(":"); d[key] = int(val.split()[0]) * 1024 / 1e6
        return d
    except OSError:
        return None

def touch(arr, frac):                                    # read a fraction of the array (sum it, without making a copy)
    return float(np.sum(arr[:int(len(arr) * frac)], dtype=np.float64))

path = os.path.join(tempfile.mkdtemp(prefix="c14_s08_"), "weights.npy")
np.save(path, np.random.default_rng(0).standard_normal(50_000_000, dtype=np.float32).astype(np.float16))
print(f"file size: {os.path.getsize(path):,} bytes")
base = rss_mb()
if base is None:
    print("/proc/self/status is not available on this system (it exists on Linux, Colab and Kaggle)")
else:
    def report(label):
        now = rss_mb()
        print(f"{label:38s} file-backed +{now['RssFile'] - base['RssFile']:6.1f} MB | app memory +{now['RssAnon'] - base['RssAnon']:6.1f} MB")
    w = np.load(path, mmap_mode="r"); report("memory-mapped, nothing read yet")
    touch(w, 0.25); report("memory-mapped, first quarter read")
    touch(w, 1.0); report("memory-mapped, everything read")
    del w; report("unmapped")
    w = np.load(path); report("np.load: full copy into app memory")
    del w; report("copy deleted")
print(f"runtime so far {time.time() - t_start:.0f} s")

What to notice¶

(Written from the saved run. Every number except the two timings in section 3 is exact and will match yours.)

  1. For this CNN, activations set the peak, not weights. All the weights take 17,040 bytes in int8, but the largest input + output pair takes 138,240 bytes: layer 5, the stride-2 depthwise convolution that reads the 48 × 48 × 48 expanded tensor. That is eight times the weights. Keeping every activation, as training must, would need 366,912 bytes; in float32 the peak would be 552,960 bytes. The peak sits in the early, high-resolution layers: none of the last six layers needs more than 70 kB.
  2. The execution order changed the peak by a quarter. Running both expansions first (breadth-first) peaked at 175,104 bytes; finishing one branch before starting the other (depth-first) peaked at 129,024 bytes, 26% less. Trying all 20 valid orders gave a best of 129,024 and a worst of 175,104, so depth-first was optimal here. The skip connection keeps the block's input alive the whole time.
  3. Patch-based execution gave the same output with a lower peak, at a price. Every patch size matched the full computation to 6.0e-08 (float rounding). The peak fell from 138,240 bytes to 92,208 with 2 × 2 patches, 65,136 with 4 × 4 (2.12 times lower) and 58,080 with 8 × 8. The gain flattens because the whole input and output of the stage (27,648 bytes each) stay in memory, while the repeated halo work grows from 14.3% extra MACs (2 × 2) to 65.0% (8 × 8). On this server CPU, 4 × 4 patches took 5.63 ms against 0.56 ms layer by layer: 80 small convolution calls from Python plus 30% more arithmetic. On a microcontroller whose RAM cannot hold the layer-by-layer peak, the slower version is the one that runs at all.
  4. The KV cache depends on the attention configuration. Example A in float16 needs 134.2 MB at 4,096 tokens, and the tensors actually allocated took exactly the formula's 134,217,728 bytes; 30,517 tokens fit in 1 GB, or 122,070 in int4. Example B, with more layers and larger heads, needs 469.8 MB at 4,096 tokens, and only 8,719 tokens fit in 1 GB in float16. Example C, with one KV head and a 512-token window in 22 of its 26 layers, needs 28.3 MB at 4,096 tokens; its 1 GB limit (241,324 tokens) is far beyond the context length a small model is usually trained for (see max_position_embeddings in its config). Without grouped-query attention, A would need 536.9 MB at 4,096 tokens, four times more.
  5. Memory-mapping costs RAM only for what is read. Mapping the 100 MB file used no memory until it was read; reading a quarter added 25.2 MB of file-backed pages, reading everything 100.0 MB, and the app's own memory did not grow. np.load instead copied all 100.0 MB into app memory. The operating system can drop file-backed pages when memory is short and read them from the file again later (which costs time); it cannot drop the app's own copy that way.
