1. By hand first: a cache with two places¶

A model server keeps things that it has already computed, so that it does not compute them again. Memory is limited, so it must also decide what to throw away. Take a cache with room for two items and this trace of six requests. Think of A, B and C as three system prompts whose computed states we would like to keep:

A B A C A B

A request is a hit if the item is in the cache, and a miss if it is not. After a miss the item is computed and stored. If the cache is full, one stored item must leave first: this is an eviction. Three rules for choosing it:

  • LRU (least recently used): evict the item whose last use is the oldest;
  • FIFO (first in, first out): evict the item that entered first, however often it was used after that;
  • Belady's rule (Belady 1966): evict the item whose next request is furthest in the future. No rule has fewer misses, but it must know the future, so it is a yardstick and not a policy that a server can run.

Do it on paper first: write the content of the cache after every request for each rule, and count the hits. Then do the same for the trace A B C A B C.

import math, time, heapq, random
from collections import OrderedDict, deque
import numpy as np
import matplotlib.pyplot as plt

t_start = time.time()

def small_cache(trace, capacity, rule):
    # A cache as a plain list, good enough for a hand example. cache[0] is the next item to leave.
    cache, hits, rows = [], 0, []
    for t, x in enumerate(trace):
        hit, evicted = x in cache, "-"
        if hit:
            hits += 1
            if rule == "LRU":                                # a hit makes the item the most recently used one
                cache.remove(x); cache.append(x)
        else:
            if len(cache) == capacity:
                if rule == "Belady":                         # the item whose next request is furthest away
                    future = trace[t + 1:]
                    evicted = max(cache, key=lambda y: future.index(y) if y in future else len(trace))
                else:                                        # LRU and FIFO both evict cache[0]; they differ in what a hit does
                    evicted = cache[0]
                cache.remove(evicted)
            cache.append(x)
        rows.append((x, "hit" if hit else "miss", evicted, " ".join(map(str, cache))))
    return hits, rows

trace = "ABACAB"
hits, rows = small_cache(trace, 2, "LRU")
print(f"trace {' '.join(trace)}, cache of 2 places, rule LRU (the cache is printed from least to most recently used)")
print("request | result | evicted | cache after")
for x, result, evicted, content in rows:
    print(f"   {x}    | {result:6s} |    {evicted}    | {content}")
for tr in ["ABACAB", "ABCABC"]:
    print(f"trace {' '.join(tr)}: hits out of {len(tr)}: " + ", ".join(f"{rule} {small_cache(tr, 2, rule)[0]}" for rule in ["LRU", "FIFO", "Belady"]))

2. The KV cache is memoization: count the attention scores¶

A decoder produces one token per step, and at every step attention reads all the earlier tokens (Course 4 session 1). The simple way is to call the whole model again on the whole sequence. With $t$ tokens it then computes a $t \times t$ table of attention scores in every layer, so producing $n$ tokens costs

$$1^2 + 2^2 + \dots + n^2 = \frac{n(n+1)(2n+1)}{6} \approx \frac{n^3}{3} \text{ scores per layer.}$$

But a decoder is causal: a token looks only backwards. So the key and the value of an earlier token do not change when a new token arrives. Store them (this store is the KV cache), and at step $t$ compute only the new token's row of the table, $t$ scores:

$$1 + 2 + \dots + n = \frac{n(n+1)}{2} \approx \frac{n^2}{2} \text{ scores per layer.}$$

This is memoization, the idea behind dynamic programming in session 5: keep a result instead of computing it again. The price is memory: one key and one value per token and per layer. Course 4 session 4 builds a KV cache inside a small transformer and times it, and Course 11 session 8 works out its size in bytes. Here we count.

The decoder below is tiny: 2 layers, 1 attention head, width 16 and random weights. It does not write good text, and it does not have to: we count its work. We produce 512 tokens twice, without and with the cache, count every score that the code computes, and check that both runs give the same tokens and the same logits. Then we change one token in the middle of a sequence and look at which stored entries are still correct.

One detail about the constant: we count every entry of the score table that the code computes. The causal mask throws away the upper half of the $t \times t$ table, so a careful implementation without a cache could compute about half, $n^3/6$. The exponent stays 3.

D_MODEL, N_LAYERS, VOCAB_TOY, N_GEN = 16, 2, 50, 512
rng = np.random.default_rng(0)
model = {"E": rng.normal(0, 1, (VOCAB_TOY, D_MODEL)),                        # token embeddings
         "P": rng.normal(0, 1, (N_GEN, D_MODEL)),                            # position embeddings
         "layers": [{name: rng.normal(0, 1, (D_MODEL, D_MODEL)) / math.sqrt(D_MODEL) for name in ("Wq", "Wk", "Wv", "Wo")}
                    for _ in range(N_LAYERS)],
         "U": rng.normal(0, 1, (D_MODEL, VOCAB_TOY)) / math.sqrt(D_MODEL)}   # output layer: width -> vocabulary

def softmax(z):
    e = np.exp(z - z.max(axis=-1, keepdims=True))
    return e / e.sum(axis=-1, keepdims=True)

def forward_full(tokens, count):
    # No cache: the whole model on all t tokens. Returns the logits for the next token.
    t = len(tokens)
    x = model["E"][tokens] + model["P"][:t]
    mask = np.triu(np.full((t, t), -np.inf), k=1)                # a token must not look at later tokens
    for layer in model["layers"]:
        q, k, v = x @ layer["Wq"], x @ layer["Wk"], x @ layer["Wv"]
        scores = q @ k.T / math.sqrt(D_MODEL)                    # the t x t table of attention scores
        count[0] += scores.size
        x = x + softmax(scores + mask) @ v @ layer["Wo"]
    return x[-1] @ model["U"]

def new_cache(max_len):
    return {"K": np.zeros((N_LAYERS, max_len, D_MODEL)), "V": np.zeros((N_LAYERS, max_len, D_MODEL)), "t": 0}

def forward_step(token, cache, count):
    # With a cache: only the new token. cache["K"][l] and cache["V"][l] hold the keys and values of layer l.
    t = cache["t"]
    x = model["E"][token] + model["P"][t]
    for l, layer in enumerate(model["layers"]):
        cache["K"][l, t], cache["V"][l, t] = x @ layer["Wk"], x @ layer["Wv"]      # store the new key and value
        scores = cache["K"][l, :t + 1] @ (x @ layer["Wq"]) / math.sqrt(D_MODEL)    # one row of the table: t + 1 scores
        count[0] += scores.size
        x = x + softmax(scores) @ cache["V"][l, :t + 1] @ layer["Wo"]
    cache["t"] = t + 1
    return x @ model["U"]

def generate(n_new, use_cache):
    tokens, count, counts, logits_seen = [0], [0], [], []        # token 0 starts the sequence
    cache = new_cache(n_new)
    for step in range(n_new):
        logits = forward_step(tokens[-1], cache, count) if use_cache else forward_full(np.array(tokens), count)
        tokens.append(int(np.argmax(logits)))                    # greedy decoding (session 7)
        counts.append(count[0]); logits_seen.append(logits)
    return tokens, np.array(counts), np.array(logits_seen)

3. An LRU cache from scratch: a hash map and a doubly linked list¶

Section 1 kept the cache in a Python list. Finding an item scans the list, so a request costs $O(k)$ for a cache of $k$ items. The classic design makes every operation $O(1)$:

  • a hash map (a dict, session 2) from the key to a node: expected $O(1)$ to find an item;
  • a doubly linked list of the nodes in order of last use. A node knows both its neighbours, so we can unlink it from the middle in $O(1)$ and put it at the front in $O(1)$. The node at the back is the least recently used, the one to evict.

So get and put make a fixed number of pointer writes, whatever the size of the cache. (The list work is $O(1)$ in the worst case; the hash-map lookup is $O(1)$ in expectation.) Python's collections.OrderedDict is built the same way, so we use it to check our class on random traces.

Then we count the work of both designs on a skewed workload. Requests to a cache are rarely uniform: a few items are asked for very often and most are rare. We model this with a Zipf distribution over 5,000 items, where the item of rank $r$ has probability proportional to $1/r$. The workload is synthetic: 30,000 requests drawn independently.

class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key, self.value, self.prev, self.next = key, value, None, None

class LRUCache:
    def __init__(self, capacity):
        self.capacity, self.map = capacity, {}               # key -> node
        self.head, self.tail = Node(), Node()                # two empty guard nodes: head.next is the most recently used item
        self.head.next, self.tail.prev = self.tail, self.head
        self.pointer_writes = 0
    def _unlink(self, node):
        node.prev.next, node.next.prev = node.next, node.prev
        self.pointer_writes += 2
    def _push_front(self, node):
        node.prev, node.next = self.head, self.head.next
        self.head.next.prev = node
        self.head.next = node
        self.pointer_writes += 4
    def get(self, key):
        node = self.map.get(key)
        if node is None:
            return None
        self._unlink(node); self._push_front(node)           # a hit: now the most recently used
        return node.value
    def put(self, key, value):
        # Store a value. Returns the key that was evicted, or None.
        node, evicted = self.map.get(key), None
        if node is not None:
            node.value = value
            self._unlink(node); self._push_front(node)
            return None
        if len(self.map) == self.capacity:
            last = self.tail.prev                            # the least recently used item
            self._unlink(last); del self.map[last.key]; evicted = last.key
        node = Node(key, value)
        self.map[key] = node; self._push_front(node)
        return evicted
    def keys(self):                                          # from most to least recently used
        out, node = [], self.head.next
        while node is not self.tail:
            out.append(node.key); node = node.next
        return out

def run_lru(requests, capacity):
    cache, hits = LRUCache(capacity), 0
    for x in requests:
        if cache.get(x) is None:
            cache.put(x, True)                               # a miss: compute and store
        else:
            hits += 1
    return hits, cache.pointer_writes

def run_list_lru(requests, capacity):
    # The list design, in its kindest form: most recently used first, so popular items are found early.
    cache, hits, examined = [], 0, 0
    for x in requests:
        if x in cache:
            i = cache.index(x)
            examined += i + 1; hits += 1; del cache[i]
        else:
            examined += len(cache)                           # a miss looks at every item
            if len(cache) == capacity:
                cache.pop()
        cache.insert(0, x)
    return hits, examined

4. Which item should leave? LRU, FIFO, random and the best possible¶

Now four eviction rules on the same 30,000 requests, for several cache sizes:

  • LRU, with the class of section 3;
  • FIFO, with a queue (collections.deque) and a set;
  • random: evict a stored item chosen uniformly at random;
  • Belady's rule: evict the item whose next request is furthest away. We first compute, for every request, when the same item is requested next. A max-heap (session 7) then gives the stored item with the furthest next request in $O(\log k)$; old heap entries are skipped when they come out (lazy deletion, as in session 3).

How far can LRU be from the best possible? Sleator & Tarjan (1985) proved that on any trace LRU with $k$ places has at most about $k$ times as many misses as the best possible rule with $k$ places, and that no deterministic rule that works without knowing the future has a better guarantee. The factor $k$ is a worst case. We measure the factor on the Zipf workload, and on the trace that is worst for LRU: $k + 1$ items requested in a cycle, so that every request asks for the one item that LRU has just evicted.

Before the experiment, the three fast implementations are checked against the slow list version of section 1 on 300 short random traces.

def run_fifo(requests, capacity):
    stored, order, hits = set(), deque(), 0
    for x in requests:
        if x in stored:
            hits += 1
        else:
            if len(stored) == capacity:
                stored.discard(order.popleft())              # the item that entered first
            stored.add(x); order.append(x)
    return hits

def run_random(requests, capacity, seed=0):
    rnd, items, place, hits = random.Random(seed), [], {}, 0  # place[x] = index of x in items
    for x in requests:
        if x in place:
            hits += 1
        elif len(items) < capacity:
            place[x] = len(items); items.append(x)
        else:
            i = rnd.randrange(capacity)                      # a random victim; the new item takes its place
            del place[items[i]]
            items[i] = x; place[x] = i
    return hits

def run_belady(requests, capacity):
    n = len(requests)
    next_use, last_seen = [0] * n, {}
    for t in range(n - 1, -1, -1):                           # next_use[t]: when the item of request t is requested again
        next_use[t] = last_seen.get(requests[t], n + t)      # "never again" = beyond the end
        last_seen[requests[t]] = t
    stored, heap, hits = {}, [], 0                           # stored[x] = next request of x; heap of (-next request, x)
    for t, x in enumerate(requests):
        if x in stored:
            hits += 1
        elif len(stored) == capacity:
            while True:
                neg, victim = heapq.heappop(heap)
                if stored.get(victim) == -neg:               # skip entries that are out of date
                    del stored[victim]
                    break
        stored[x] = next_use[t]
        heapq.heappush(heap, (-next_use[t], x))
    return hits

5. A prefix tree of cached prompts¶

The KV cache of section 2 lives inside one request. Can a second request use it? Yes, if both prompts start with the same tokens: section 2 showed that the stored entries of a prefix do not depend on what comes after it. Real prompts share long prefixes: the same system prompt, the same worked examples or the same long document, and then a different question.

So keep the cached states in a prefix tree (a trie, as in sessions 3 and 8) over token ids. A node stands for one token after the path that leads to it, and holds the keys and values of that token. For a new prompt, walk down from the root while the tokens match. The matched tokens are reused. The others must be computed, and they are added as a new branch. SGLang's RadixAttention works like this (Zheng et al. 2024). It uses a radix tree, which stores a run of tokens without a branch as one edge: fewer nodes, the same idea.

Memory is limited, so we must evict. A node in the middle cannot leave, because every node below it depends on it. Only a leaf can leave. We evict the least recently used leaf, again and again, until the tree fits; a heap of leaves ordered by last use finds it.

The workload is synthetic: 6 system prompts, 4 example blocks for each of them, and 2,000 requests. A request is a system prompt, then one of its example blocks, then a new question of 8 to 40 tokens. Token ids are random numbers below 5,000. The nodes hold no real keys and values: we only count tokens, and the capacity of the cache is a number of tokens.

class TrieNode:
    __slots__ = ("token", "parent", "children", "last_used")
    def __init__(self, token, parent):
        self.token, self.parent, self.children, self.last_used = token, parent, {}, 0

class PrefixCache:
    def __init__(self, capacity):
        self.capacity, self.size, self.clock = capacity, 0, 0   # capacity and size are counted in tokens (= nodes)
        self.root = TrieNode(None, None)
        self.leaves, self.pushes, self.evicted = [], 0, 0        # heap of (last use, tie-breaker, node)
    def _push(self, node):
        self.pushes += 1
        heapq.heappush(self.leaves, (node.last_used, self.pushes, node))
    def request(self, tokens):
        # Returns how many tokens at the start of the prompt were found in the tree.
        self.clock += 1
        node, reused = self.root, 0
        for tok in tokens:                                   # 1. walk down while the prompt matches
            child = node.children.get(tok)
            if child is None:
                break
            node = child; node.last_used = self.clock; reused += 1
        for tok in tokens[reused:]:                          # 2. the model computes the other tokens; store them as a new branch
            child = TrieNode(tok, node); child.last_used = self.clock
            node.children[tok] = child; node = child
        self.size += len(tokens) - reused
        if node is not self.root:
            self._push(node)
        while self.size > self.capacity:                     # 3. evict least recently used leaves until the tree fits
            last_used, _, leaf = heapq.heappop(self.leaves)
            if leaf.children or leaf.last_used != last_used or leaf.parent.children.get(leaf.token) is not leaf:
                continue                                     # out of date: not a leaf any more, used again, or already evicted
            del leaf.parent.children[leaf.token]
            self.size -= 1; self.evicted += 1
            if leaf.parent is not self.root and not leaf.parent.children:
                self._push(leaf.parent)                      # the parent has become a leaf
        return reused

6. Batches and padding¶

A graphics processor handles a batch of sequences in much less time than it would need for the same sequences one after another, so a server wants to fill its batches. The first obstacle is that sequences have different lengths. To put them into one array, the short ones are padded to the length of the longest in the batch, and the work on the padding is thrown away.

If the lengths are known in advance (the prompts of an offline job, for example), sort the inputs by length before cutting them into batches. Each batch then holds inputs of nearly the same length. Course 6 session 9 uses this to fit inference into a competition's time limit.

Below: 4,096 inputs whose lengths follow a heavy-tailed distribution (most are short, a few are very long), cut into batches of 32 in three ways. The count is exact: token places computed, real or padding. The lengths are synthetic.

rng = np.random.default_rng(0)
def heavy_tailed_lengths(n, rng):
    # lognormal: median about 33 tokens, mean about 54, cut off at 512
    return np.clip(np.round(rng.lognormal(3.5, 1.0, n)), 1, 512).astype(int)

BATCH = 32
def padded_places(order):
    batches = [lengths[order[i:i + BATCH]] for i in range(0, len(order), BATCH)]
    return sum(len(b) * int(b.max()) for b in batches)       # every sequence is padded to the longest of its batch

7. A batching simulator: static against continuous batching¶

In generation the second obstacle is worse: nobody knows the length of an output until the model produces its end token, so we cannot sort by it. And requests arrive at different moments.

This section is a simulation, not a measurement of a real server. Its rules:

  • the server has $B = 8$ slots; in one step every running sequence produces one token;
  • a step takes the same time however many slots are in use, and reading the prompt costs nothing (both are simplifications);
  • output lengths come from the heavy-tailed distribution of section 6, and requests arrive at random moments (a Poisson process). Both are made up.

Two policies, both first come, first served:

  • static batching: when the server is free, it takes up to 8 waiting requests and runs them until the longest has finished. Nobody joins on the way. A slot whose sequence has finished keeps being computed as padding. (We are generous: a request counts as finished when its own last token is produced, not when the batch ends.)
  • continuous batching: after every step, finished sequences leave and waiting requests take the free slots. Orca introduced this as iteration-level scheduling (Yu et al. 2022). The name continuous batching came later; servers such as vLLM use it today.

First a backlog: 2,000 requests that are all waiting at the start, as in an offline job. Then requests that arrive over time, at several loads. The load is the number of tokens requested in each step, divided by the 8 that the server can produce. Everything is counted in steps, so the numbers are the same on every run.

The last part counts memory. A running sequence must store a key and a value for each of its tokens. A simple server reserves room for the longest allowed output (512 tokens here) when a sequence starts. PagedAttention (Kwon et al. 2023) cuts the memory into small fixed-size blocks instead and gives a sequence one more block only when its last block is full; a block table records which blocks belong to which sequence, like the page table of an operating system. We count the peak memory in token places for both rules.

B = 8
def run_static(arrivals, lengths, order_by_length=False):
    n = len(arrivals)
    first, finish = np.zeros(n, dtype=int), np.zeros(n, dtype=int)
    t, i, places = 0, 0, 0                                   # places: slot-steps computed, real tokens and padding
    queue = np.argsort(lengths, kind="stable") if order_by_length else np.arange(n)   # sorting needs the lengths in advance
    while i < n:
        t = max(t, int(arrivals[queue[i]]))                  # wait until a request is there
        j = i
        while j < n and j - i < B and arrivals[queue[j]] <= t:
            j += 1
        batch = queue[i:j]                                   # up to B waiting requests
        run = int(lengths[batch].max())                      # the batch runs until its longest sequence ends
        first[batch] = t + 1; finish[batch] = t + lengths[batch]
        places += len(batch) * run
        t += run; i = j
    return first, finish, places, t

def run_continuous(arrivals, lengths):
    n = len(arrivals)
    first, finish = np.zeros(n, dtype=int), np.zeros(n, dtype=int)
    left = {}                                                # running request -> tokens still to produce
    t, i, done, places = 0, 0, 0, 0
    while done < n:
        while i < n and len(left) < B and arrivals[i] <= t:  # free slots go to waiting requests
            left[i] = int(lengths[i]); first[i] = t + 1; i += 1
        if not left:
            t = int(arrivals[i]); continue                   # nothing is running: jump to the next arrival
        t += 1; places += len(left)                          # one step: every running sequence produces one token
        for r in [r for r, m in left.items() if m == 1]:
            finish[r] = t; del left[r]; done += 1
        for r in left:
            left[r] -= 1
    return first, finish, places, t

What to notice¶

(Written from the saved run. Every count below is the same on every run, because the seeds are fixed and the simulator counts steps. The lines that contain the word "time" change from run to run. Sections 3 to 7 use synthetic workloads, and section 7 is a simulation, not a measurement of a real server.)

  1. The eviction rule matters already for six requests. On A B A C A B with two places, LRU had 2 hits, FIFO 1 and Belady's rule 2. On A B C A B C, LRU and FIFO had 0 hits and Belady's rule 2: three items in a cycle are the worst case for a cache of two.
  2. The KV cache changes the exponent, not the output. The counted scores are exactly the formulas: for 512 tokens, 44,870,400 scores per layer without the cache ($n^3/3$ times 1.003) and 131,328 with it ($n^2/2$ times 1.002), a factor of 341.7. Both runs produced the same 512 tokens, and the logits agree to $1.8 \times 10^{-14}$ (the two versions add the same numbers in a different order). The price is memory: 32,768 stored numbers for this toy model. In the saved run the version without the cache needed 4.44 seconds and the cached one 0.02 seconds; these two timings change from run to run, the counts do not.
  3. A cached prefix stays valid; everything after a change does not. After one token was changed at position 20, layer 2 kept the same key and value at exactly the 20 positions before it and at none of the 43 positions after it. Layer 1 changed only at position 20, because its keys and values are computed from a token's own embedding and position. A real model has many layers, so in practice everything from the changed token on must be computed again.
  4. A hash map and a doubly linked list give O(1), and the count shows it. Our class agreed with OrderedDict on 100,000 random operations. It made about 6 pointer writes for each request at every capacity (6.00 at 16, 5.93 at 1,024), while the list version examined 14.2, 47.7, 145.8 and 382.6 items for each request at capacities 16, 64, 256 and 1,024. Look at the timing lines too: at capacity 16 the list version was the faster one in the saved run, because its scan runs inside the interpreter's C code. The better Big-O wins only when the cache is large enough (session 1 made the same point).
  5. LRU is better than FIFO, but not by much, and far from the best possible. On the Zipf workload the hit rates at capacity 64 were LRU 0.373, FIFO 0.324, random 0.323 and Belady's rule 0.572. FIFO and random eviction were almost equal at every size. LRU had 1.29 to 1.66 times as many misses as Belady's rule, far below the worst-case factor $k$. The worst case is real, though: on the cycle of 9 items with 8 places LRU missed all 9,000 requests and Belady's rule 1,132, a factor of 7.95. One result we did not plan for: random eviction missed only 2,010 of these requests. The cycle is built against a rule whose choices can be predicted, and a random choice cannot be predicted.
  6. A prefix tree turns shared prompts into saved work, if it has room. A cache of whole prompts had 0 hits, because every question is new. The prefix tree reused 0.166 of all prompt tokens with room for 500 tokens, 0.472 with 2,000, 0.921 with 8,000 and 0.959 with 16,000 or more; 0.959 is the most that this workload allows. With 8,000 places the tree could have held all 7,954 shared tokens, but it reused less than the maximum: LRU keeps the most recent questions, which nobody will ask again, and evicts older shared blocks. Position matters more than size: changing the last token of a prompt of 668 tokens kept 667 tokens, changing the token at position 10 kept 10, and one new token in front kept 0.
  7. Sorting by length removes most padding, when the lengths are known. Batches of 32 in order of arrival computed 1,110,432 token places for 218,398 real tokens: 80.3% padding. Sorting inside pools of 512 left 27.3%, and sorting everything left 3.6%.
  8. Static batching wastes slots; continuous batching fills them. With a backlog of 2,000 requests, static batches needed 41,861 steps and only 32.1% of the slot places produced a token. Continuous batching needed 13,532 steps (99.4%), close to the lower bound of 13,456. If the output lengths were known in advance, sorted static batches would need 13,676 steps (98.4%), almost as good: the gain of continuous batching comes from not knowing the lengths and from requests that arrive later.
  9. With arrivals over time the difference is waiting. At load 0.2 the mean latency was 152.5 steps with static batching and 53.8 with continuous batching (the mean output length itself is 53.8), and the mean wait for the first token was 99.7 steps against 1.0. At loads 0.5 and 0.8 static batching could not keep up: the queue grew for as long as requests arrived, so its latencies (6,588.7 and 11,898.7 steps) depend on how long we simulate and are not steady values. Continuous batching stayed at 54.3 and 64.1 steps, with a 95th percentile of 188.0 at load 0.8.
  10. Blocks instead of reservations. At load 0.8, reserving 512 places for each running sequence needs 4,096 token places at the peak. Blocks of 16 places, taken when needed, need 1,296, and the stored tokens themselves 1,227. A sequence can waste at most 15 places in its last block.
