1. By hand first: three merges on five words¶

Byte-pair encoding (BPE) builds a vocabulary of word pieces by repeating one step: count every pair of neighbouring symbols, merge the most frequent pair into one new symbol, and count again (Sennrich et al. 2016; the idea comes from a compression method, Gage 1994). Course 4 session 2 and Course 5 session 4 explain what tokenizers are for and how to choose one for Bangla. This notebook is about the algorithm: its data structures and its cost.

On paper: the corpus is five words, nana nani nan ana dana, each seen once. Start from single letters.

  1. Count all pairs of neighbours inside the words. Pairs never cross a word boundary.
  2. Merge the most frequent pair everywhere, from left to right, into a new symbol.
  3. Do this three times in all. How many symbols are left?

Ties. If two pairs have the same count, take the pair whose first symbol is older: single letters in alphabetical order come first, then merged symbols in the order in which they were made. If the first symbols are equal, compare the second symbols in the same way. (In the code every symbol has a number, its id: 0 to 255 for the single bytes, then 256, 257, … for the merges. The rule is "the smallest pair of ids".)

Then run the cell. Its loop is the whole naive algorithm.

import os

t_start = time.time()

def show(token):
    # a readable form of a token (bytes): its text with the space written as "_", or hex bytes if it is not valid UTF-8 alone
    try:
        return token.decode("utf-8").replace(" ", "_")
    except UnicodeDecodeError:
        return "<" + token.hex(" ") + ">"

def count_pairs(words, freqs):
    # one pass over every symbol of every word: how often does each pair of neighbours occur?
    counts = {}
    for w, f in zip(words, freqs):
        for pair in zip(w, w[1:]):
            counts[pair] = counts.get(pair, 0) + f
    return counts

def best_pair(counts):
    # the highest count; among equal counts, the smallest pair of ids
    return min(counts, key=lambda pair: (-counts[pair], pair))

def merge_word(w, pair, new_id):
    # replace every occurrence of the pair in one word, from left to right
    out, i = [], 0
    while i < len(w):
        if i + 1 < len(w) and w[i] == pair[0] and w[i + 1] == pair[1]:
            out.append(new_id); i += 2
        else:
            out.append(w[i]); i += 1
    return out

def spell(words, vocab):
    return " | ".join(" ".join(show(vocab[t]) for t in w) for w in words)

tiny = [b"nana", b"nani", b"nan", b"ana", b"dana"]

tiny_merges = []

2. The corpus: made-up words with a Zipf law, and two real paragraphs¶

Real text has a few very frequent words and a long tail of rare ones: the word of rank $r$ has a frequency roughly proportional to $1/r$ (Zipf's law). Our corpus imitates this with synthetic data: 8,000 made-up words built from random syllables, and a text of 60,000 running words drawn with probability proportional to $1/r$. We add two short paragraphs written for this notebook, one in English and one in Bangla, so that the corpus also holds a little text of a kind that is rare in it.

Three conventions, close to those of byte-level tokenizers such as GPT-2's (GPT-2 splits text with a regular expression that also separates digits and punctuation; we split at spaces only):

  • a symbol is a byte of the UTF-8 encoding, so the starting vocabulary is the 256 byte values and no text can be "unknown";
  • the text is split at spaces, and every word keeps its leading space (printed as _), so that the tokens can be glued back into the text;
  • merges never cross a word boundary.

A trainer can read the token stream (every running word, in order) or the word types (each different word once, with its frequency). The cell builds both. The Bangla paragraph is first normalized to NFC, so that each character has one spelling in code points (Course 5 session 2).

CONS, VOWELS = "bcdfghjklmnprstvz", "aeiou"
SYLLABLES = [c + v for c in CONS for v in VOWELS]             # 85 syllables such as "ba", "ke", "zu"

def make_words(n, seed=0):
    # n different made-up words of two to four syllables, in a fixed order
    r, words, seen = random.Random(seed), [], set()
    while len(words) < n:
        w = "".join(r.choice(SYLLABLES) for _ in range(r.choice([2, 3, 3, 4])))
        if w not in seen:
            seen.add(w); words.append(w)
    return words

3. The naive trainer: recount everything after every merge¶

train_naive is the loop of section 1 as a function. Every merge costs one full pass over the corpus to count the pairs and one more to apply the merge. With $N$ symbols and $M$ merges that is $O(N \cdot M)$.

Its work is easy to count exactly: a pass over a word of $L$ symbols looks at $L - 1$ pairs. We run it

  • on the token stream, every running word separately, for 10 merges only;
  • on the word types with their frequencies: a pair inside a word that occurs 50 times is looked at once and counted with weight 50. This is the first speed-up of every real trainer (the algorithm of Sennrich et al. 2016 runs on such a dictionary): $N$ shrinks from the length of the text to the total length of the different words.

We also record how often the best pair was chosen among several pairs with the same count.

def train_naive(word_list, freqs, num_merges):
    words = [list(w) for w in word_list]
    vocab = [bytes([i]) for i in range(256)]
    merges, log = [], {"count": [], "work": [], "tied": [], "time": []}
    t0 = time.perf_counter()
    for _ in range(num_merges):
        counts = count_pairs(words, freqs)                           # recount everything
        if not counts:
            break
        log["work"].append(sum(len(w) - 1 for w in words))           # the pairs that this recount looked at
        pair = best_pair(counts)
        vocab.append(vocab[pair[0]] + vocab[pair[1]])
        words = [merge_word(w, pair, len(vocab) - 1) for w in words]  # one more pass to apply the merge
        merges.append(pair)
        log["count"].append(counts[pair])
        log["tied"].append(sum(1 for c in counts.values() if c == counts[pair]))
        log["time"].append(time.perf_counter() - t0)
    return merges, vocab, words, log

def merge_names(merges, vocab):
    return "  ".join(f"{show(vocab[a])}+{show(vocab[b])}" for a, b in merges)

4. The indexed trainer: linked symbols, a pair index and a heap¶

Most of the naive trainer's work is wasted. A merge changes the text only where the merged pair occurs, and there it changes only the pairs that touch it. If a word reads … x a b y … and we merge a b into ab, exactly five counts change: the occurrence of (a, b) disappears, (x, a) and (b, y) lose one occurrence each, and (x, ab) and (ab, y) gain one each. Three data structures let us do this and nothing more:

  1. Linked lists. Each word is a doubly linked list of symbols, so two neighbours are fused in $O(1)$ without shifting an array. The lists live in flat arrays: sym[p] is the symbol at position p, and prv[p] and nxt[p] are the positions of its neighbours.
  2. A pair index. count[pair] is the pair's frequency and where[pair] is the set of positions where it starts (two hash tables, session 2). A merge visits only those positions.
  3. A max-heap with lazy deletion. The heap holds (count, pair) entries, with the most frequent pair on top. When a count goes down we do not search the heap for its entry. The old entry stays, and when an entry reaches the top we compare it with the true count: if it is stale, we push it back with the true count and take the next one. This works because the count of an existing pair never goes up: only pairs that contain the brand-new symbol gain occurrences.

Every merged occurrence removes one symbol, so a whole training run has fewer than $N$ of them, and each makes at most five count updates. The work is $O(N)$ updates and $O(N)$ heap operations of $O(\log N)$ each, whatever the number of merges $M$. Zouhar et al. (2023) analyse BPE formally and bring training from $O(N \cdot M)$ down to $O(N \log M)$. The reference tool of Sennrich et al., subword-nmt, also keeps an index from every pair to the words that contain it and updates its counts after each merge; it finds the best pair by scanning a dictionary, not with a heap (its file learn_bpe.py, read in November 2026).

Both trainers must make the same choice on ties, or their merge lists drift apart. Ours take the highest count and then the smallest pair of ids; a min-heap of (-count, pair) tuples does exactly that. (subword-nmt takes the largest pair on a tie, so its merges would differ from ours.) The cell asserts that the merge lists and the final cut of every word are identical. It then runs the indexed trainer for 4,000 merges, which the naive trainer would need minutes for.

def train_indexed(word_list, freqs, num_merges):
    t0 = time.perf_counter()
    # 1. every word as a linked list in flat arrays; -1 marks "no neighbour"
    sym, prv, nxt, weight, first = [], [], [], [], []
    for w, f in zip(word_list, freqs):
        start = len(sym); first.append(start)
        for j, byte in enumerate(w):
            sym.append(byte); weight.append(f)
            prv.append(start + j - 1 if j > 0 else -1)
            nxt.append(start + j + 1 if j + 1 < len(w) else -1)
    # 2. the pair counts and the pair index
    count, where = {}, {}
    for p in range(len(sym)):
        if nxt[p] != -1:
            pair = (sym[p], sym[nxt[p]])
            count[pair] = count.get(pair, 0) + weight[p]
            where.setdefault(pair, set()).add(p)
    # 3. the heap; heapq is a min-heap, so we store -count
    heap = [(-c, pair) for pair, c in count.items()]
    heapq.heapify(heap)
    vocab = [bytes([i]) for i in range(256)]
    merges = []
    log = {"count": [], "work": [], "symbols": [], "time": [], "pushes": len(heap), "stale": 0, "index time": time.perf_counter() - t0}
    n_symbols = len(sym)
    while len(merges) < num_merges and heap:
        neg, pair = heapq.heappop(heap)
        c = count.get(pair, 0)
        if c != -neg:                                    # stale: the count has gone down since this entry was pushed
            log["stale"] += 1
            if c > 0:
                heapq.heappush(heap, (-c, pair)); log["pushes"] += 1
            continue
        a, b = pair
        new_id = len(vocab)
        vocab.append(vocab[a] + vocab[b])
        log["symbols"].append(n_symbols)
        updates, created = 0, {}
        for p in sorted(where[pair]):                    # only the places where the pair occurs, from left to right
            q = nxt[p]
            if sym[p] != a or q == -1 or sym[q] != b:    # gone: it overlapped an occurrence merged just before (as in "a a a")
                continue
            f, left, right = weight[p], prv[p], nxt[q]
            if left != -1:                               # (x, a) becomes (x, ab)
                old, new = (sym[left], a), (sym[left], new_id)
                count[old] -= f; where[old].discard(left)
                count[new] = count.get(new, 0) + f; where.setdefault(new, set()).add(left)
                created[new] = None; updates += 2
            if right != -1:                              # (b, y) becomes (ab, y)
                old, new = (b, sym[right]), (new_id, sym[right])
                count[old] -= f; where[old].discard(q)
                count[new] = count.get(new, 0) + f; where.setdefault(new, set()).add(p)
                created[new] = None; updates += 2
            sym[p], sym[q] = new_id, -1                  # position p now holds the new symbol; q leaves the list
            nxt[p] = right
            if right != -1:
                prv[right] = p
            updates += 1; n_symbols -= 1                 # the occurrence of (a, b) itself
        del count[pair], where[pair]
        for new in created:                              # the new pairs enter the heap once, with their final counts
            if count[new] > 0:
                heapq.heappush(heap, (-count[new], new)); log["pushes"] += 1
        merges.append(pair)
        log["count"].append(c); log["work"].append(updates); log["time"].append(time.perf_counter() - t0)
    words = []                                           # read the linked lists back
    for start in first:
        w, p = [], start
        while p != -1:
            w.append(sym[p]); p = nxt[p]
        words.append(w)
    log["left"] = n_symbols
    return merges, vocab, words, log

5. Encoding: replaying merges, or the longest match in a trie¶

Training gives a list of merges. To encode a word with it, replay them: split the word into bytes, then again and again merge the pair of neighbours that was learned earliest (the lowest rank), until no pair of neighbours is in the list. A new word is cut exactly as if it had been in the training corpus. A word of $L$ bytes takes up to $L - 1$ rounds that each look at up to $L - 1$ pairs: $O(L^2)$ in this simple form. GPT-2's reference encoder works this way.

WordPiece tokenizers (BERT's, for example) use another rule: at each position take the longest vocabulary token that matches, then continue after it. A trie makes this fast. It is a tree with one edge per byte, in which every token is a path from the root. One walk down the trie from position $i$ finds every token that starts at $i$, and we keep the last one. When a walk runs past the longest match, the extra bytes are read again later. Song et al. (2021) add failure links to the trie, the idea of Aho & Corasick (1975), so that no byte is read twice and the time is linear. Session 8 returns to tries and automata.

With the same vocabulary the two rules do not always give the same pieces. On paper first: with the three merges of section 1 the vocabulary is the single letters and na, ana, nan. Encode nana, nanana and dana by both rules. Then run the cell, which does the same for every word type of the corpus and for 1,650 made-up words that the corpus never showed.

def encode_bpe(word, rank):
    # replay the merges: always merge the pair of neighbours with the lowest rank; returns (token ids, pair look-ups)
    toks, lookups = list(word), 0
    while len(toks) > 1:
        lookups += len(toks) - 1
        pair = min(zip(toks, toks[1:]), key=lambda pr: rank.get(pr, float("inf")))
        if pair not in rank:
            break
        toks = merge_word(toks, pair, 256 + rank[pair])
    return toks, lookups

def build_trie(vocab):
    # a node is a dictionary: byte -> child node; the key -1 holds the id of the token that ends at this node
    root, nodes = {}, 1
    for token_id, token in enumerate(vocab):
        node = root
        for byte in token:
            if byte not in node:
                node[byte] = {}; nodes += 1
            node = node[byte]
        node[-1] = token_id
    return root, nodes

def encode_longest(word, root):
    # at each position, the longest token that matches; returns (token ids, trie steps)
    out, i, steps = [], 0, 0
    while i < len(word):
        node, j, best, end = root, i, None, i
        while j < len(word) and word[j] in node:
            node = node[word[j]]; j += 1; steps += 1
            if -1 in node:
                best, end = node[-1], j
        out.append(best); i = end                        # every single byte is a token, so best is never None
    return out, steps

def pieces(ids, vocab):
    return " ".join(show(vocab[t]) for t in ids)

6. A cache of whole words, and what unfamiliar text costs¶

Because of Zipf's law the same words come back again and again. Encoders therefore keep a hash table from a whole word to its tokens (GPT-2's reference encoder has such a cache dictionary). We encode the made-up text in reading order and count how often the answer is already in the table.

Then we use the vocabulary on three kinds of text: the made-up words that fill the corpus; the English and the Bangla paragraph, which are a tiny share of it; and a string with characters that never occurred in training. A byte-level vocabulary cannot fail, because every byte is a token. It can only become expensive. Course 4 session 2 measures that cost for Bangla with real tokenizers.

def encode_text(text_words, cache):
    # encode a list of words with a cache of whole words; returns (token ids, cache hits, look-ups done, look-ups a cache-free encoder would do)
    ids, hits, done, without = [], 0, 0, 0
    for w in to_words(text_words):
        if w in cache:
            hits += 1
        else:
            cache[w] = encode_bpe(w, rank)
            done += cache[w][1]
        ids.extend(cache[w][0]); without += cache[w][1]
    return ids, hits, done, without

def decode(ids):
    return b"".join(vocab[t] for t in ids).decode("utf-8")

7. Bangla: three bytes per code point, and the merges that rebuild them¶

UTF-8 writes every Bangla code point (a letter, a vowel sign, the hasanta, …) in three bytes. The first byte is always e0 and the second is a6 or a7, so most of the information is in the third byte. (The danda । is shared with other scripts and starts with e0 a5.) A byte-level tokenizer therefore starts with three tokens per Bangla code point, and it has to learn every code point back as merges.

The cell prints the bytes of a short sentence. Then it trains 60 merges on the Bangla paragraph alone. What to notice¶

(Written from the run above. The counts are exact and will be the same on your machine; the timings will not.)

  1. Three merges by hand. The five words went from 18 symbols to 12, 10 and 8. The second merge was a tie: (a, na) and (na, n) both had count 2, and the rule "smallest pair of ids" chose a + na. With the other choice the vocabulary would hold nan but not ana after two merges.
  2. Count word types, not running words. The corpus has 60,098 running words but only 6,436 different ones: 436,762 symbols in the token stream against 45,666 in the list of types, 9.6 times fewer. Both inputs gave the same first 10 merges with the same counts. The naive trainer looked at 3,400,374 pairs to find them on the token stream and at 383,289 on the types.
  3. The naive trainer pays for the whole corpus at every merge. For 1,000 merges it looked at 15,043,777 pairs. One pass became cheaper as the words got shorter (39,230 pairs for merge 1, 11,857 for merge 1,000), but it never depended on how rare the merged pair was: the last pair occurred only 18 times.
  4. The indexed trainer pays only where the pair occurs. It gave the same 1,000 merges and the same cut of all 6,436 word types (the cell asserts both), with 98,880 count updates: 152 times less work by this count, and 2.17 updates per symbol of the corpus. Merge 1 needed 1,143 updates and merge 1,000 needed 3. In the saved run the naive trainer took about 11 seconds and the indexed one less than a tenth of a second, a ratio well above 100. The two counts measure different operations (a dictionary addition, and a count update with its index and list work), so the time ratio and the count ratio need not agree; here they were of the same size.
  5. More merges are almost free. The indexed trainer made 98,880 updates in the first 1,000 merges, 103,349 in 2,000 and 110,838 in 4,000. That is far below the limit of five per symbol (228,330). The naive trainer would have looked at 43,054,125 pairs for 4,000 merges, 388 times more. This is the difference between $O(N \cdot M)$ and a cost that hardly depends on $M$. In the saved run the indexed trainer's time for 4,000 merges (0.090 s) was not even larger than its time for 1,000 (0.094 s): the difference is smaller than the noise of the timer.
  6. Lazy deletion is cheap. In 1,000 merges the heap received 13,120 entries and only 1,804 stale entries came to the top. We never had to search the heap for an entry.
  7. Ties are the rule, not the exception. 653 of the 1,000 merges were chosen among two or more pairs with the same count. The two trainers agree only because they break ties in the same way; the second exercise measures what another rule does.
  8. Replaying merges and longest match are different rules, although here they were close. Replaying the merges reproduced the trainer's cut of every word type. Longest match in the trie cut 91 of the 6,436 types differently (1.4%, covering 247 of 60,098 running words), and 22 of the 1,650 made-up words that the corpus never showed. We expected a visible difference in tokens per word, and there was almost none: 96,064 tokens against 96,057 for the whole corpus. In 88 of the 91 cases both rules used the same number of tokens, and longest match never used more. But the pieces differ: _halo is _h alo by merges and _ha lo by longest match, so a model trained with one rule and fed by the other gets other token ids for such words. By hand, nana is na na against nan a.
  9. The trie read almost every byte once. Replaying merges cost 21.26 pair look-ups per word type, the trie 7.40 steps, for words of 7.10 bytes on average. So even without failure links the trie did little re-reading on this corpus. Failure links guarantee linear time in the worst case; they would change little here.
  10. A cache of whole words works because of Zipf's law. After 1,000 words 48.2% of them had been found in the cache, after 60,000 words 89.4%, with 6,350 words in the cache. The pair look-ups fell from 1,399,240 to 134,307 (10.4 times fewer). The 423 word types that are a single token cover 68.1% of the running words.
  11. Unfamiliar text never fails, it gets expensive. The vocabulary spends 1.59 tokens per word on the made-up text, 4.29 on the English paragraph and 8.88 on the Bangla paragraph (355 tokens for 242 code points). The two paragraphs are 98 of the 60,098 words of the corpus, so few merges were learned for them. A string with characters that were never in the corpus became 21 tokens for 30 bytes and decoded back exactly.
  12. Bangla starts at three tokens per code point. The sentence has 26 code points and 70 bytes, and costs 36 tokens with the vocabulary of section 4. Trained on the Bangla paragraph alone, the first merge was e0 + a6 (count 170), which is not a character at all; the first whole code point, া, came at merge 3. Of the 60 merges, 12 gave one whole code point, 19 gave several, and 29 cut through a code point (merge 5 is া plus the first two bytes of whatever follows). The sentence went from 71 tokens to 45 after 2 merges, 27 after 20 and 18 after 60. Byte-level merges do not respect character boundaries, which is why a decoder must join the bytes of all tokens before it turns them into text.
  13. This is a small synthetic corpus and a vocabulary of 1,256 tokens. Real tokenizers train on far more text with tens of thousands of merges. There, recounting everything after each merge would be far too slow, and the three ideas of this notebook (word types with frequencies, an index from each pair to its places, and updates of only what changed) are what makes training practical.
